# Student and Parent Account Portal Readiness

Last updated: 2026-05-08

## Role and Permission Contract

- `siswa` accounts use `student_portal.*` permissions and must be linked to exactly one `users.student_id`.
- `ortu` accounts use `parent_portal.*` permissions and must be linked to exactly one `users.parent_id`.
- Admin/operator account generation requires `student_accounts.manage` or `parent_accounts.manage`.
- Profile change review requires `profile_changes.review` or admin role fallback.
- SvelteKit BFF route access is a UX and proxy guard only. Go Core API remains the security boundary.

## Account Generation Policy

- Student and parent accounts are generated by admin/operator workflows, not public self-registration.
- Temporary passwords are random and returned only in the generation response.
- Generated and reset accounts set `users.must_change_password = TRUE`.
- Password reset, deactivate, and role/profile-link changes must continue invalidating sessions/auth version through the existing user lifecycle service.

## Username and Password Policy

- Student username basis: NISN first, then local student identifier fallback with deterministic collision suffixing.
- Parent username basis: `ortu` + primary/first child NISN, then phone fallback with deterministic collision suffixing.
- Passwords must pass backend password policy. The frontend can pre-check length, but backend remains source of truth.
- First-login users may only reach `/settings/account`, password-change API, session/logout APIs, and required auth account reads until the password is changed.

## Student Self-Scope Rules

- Student portal APIs derive `student_id` from the authenticated user account.
- Browser routes use SvelteKit BFF aliases under `/api/portal/siswa/*`.
- No student portal endpoint accepts broad student listing or caller-supplied `student_id` for authorization.
- Results responses must not expose exam tokens or answer keys.

## Parent Child-Scope Rules

- Parent child APIs derive `parent_id` from the authenticated user account, not from client input or JWT `pid` alone.
- Every child-specific route checks `parent_students(parent_id, student_id)` before returning data.
- A guessed unlinked student UUID must return `403`, including schedule/results routes that would otherwise look like empty data.
- Browser routes use SvelteKit BFF aliases under `/api/portal/orang-tua/children/*`.

## Change Request Policy

- Siswa/orang tua must not directly mutate official data through portal routes.
- Official data changes use `profile_change_requests` and reviewer approval.
- Student own requests are scoped to the authenticated `users.student_id`.
- Parent own requests are scoped to the authenticated `users.parent_id`.
- Parent requests for child data require `target_student_id` and must pass the `parent_students` relation check.
- Allowed request fields are conservative: student name, birthdate, parent name, phone, address; parent name, phone, address, occupation, and NIK. NIS/NISN, class/rombel, status, username, roles, and parent-child relationships remain blocked.

## Rollback Plan

- Roll back frontend first if portal UI or BFF behavior regresses.
- Keep migration `081_student_parent_account_portal.sql` in place once applied because it is additive and contains role/permission grants plus nullable metadata.
- If parent child-scope data looks wrong, disable sidebar/route exposure for `ortu` while leaving backend checks deployed.
- If generated-account rollout is paused, do not delete created users; deactivate affected accounts through the user lifecycle workflow so sessions and auth version remain consistent.
- Never remove `parent_students` scope checks as a rollback shortcut.
